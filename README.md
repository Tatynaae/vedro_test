# Управление картографическими слоями (React + TypeScript + vedro)

Слои **температура / ветер / инсоляция**. Для каждого слоя: включение/выключение, прозрачность,
статус `loading / success / error`, повтор после ошибки. При включении идёт mock‑запрос к API со
случайной задержкой (300–1500 мс) и вероятностью ошибки 25%.

```bash
npm install
npm run dev        # http://localhost:5173, а с ?layers=150 — сценарий на 150 слоёв
npm test           # гонки, retry, изоляция рендеров
npm run lint       # ESLint strict, no-explicit-any: error
npm run build      # tsc (strict) + vite build
```

## Архитектура

```
src/
  domain/layers.ts          типы предметной области + реестр слоёв (конфиг)
  api/layerApi.ts           контракт FetchLayer + mock-реализация (поддерживает AbortSignal)
  store/
    layersStore.ts          vedro-стор, хук useLayer(id) с подпиской на один ключ
    layersController.ts     все команды и асинхронщина, защита от гонок
    LayersProvider.tsx      composition root: стор + контроллер в контексте
  components/               только отображение: читают стор, вызывают методы контроллера
  test/                     тесты контроллера (гонки) и рендеров (React Profiler)
```

Поток данных однонаправленный: **UI → Controller → vedro store → подписанные компоненты**.

### Состояние в vedro

- **Нормализованный плоский стор** `Record<LayerId, LayerState>`: один ключ верхнего уровня на
  слой. Набор ключей фиксирован при создании (vedro запрещает добавлять ключи позже), что
  естественно ложится на реестр слоёв.
- `LayerState = { enabled, opacity, request }`, где `request` — **discriminated union**
  `idle | loading | success(data) | error(error)`. Невозможные состояния вроде «есть data и есть
  error одновременно» просто нельзя записать.
- Запись идёт через `dispatch(layerId, nextLayerState)`, то есть адресно по ключу.
- Чтение:
  - `useLayer(id)` — свой хук поверх `store.on(id, cb)` + `useSyncExternalStore`;
  - `useSelector` из vedro — только для одной агрегирующей сводки (сколько включено, грузится, с ошибкой).

Почему не `useSelector` для каждой строки: я посмотрел исходники vedro 1.1.0, и на **каждый**
dispatch `useSelector` перезапускает **все** селекторы и сравнивает результаты через `JSON.stringify`,
то есть цена O(N). А `store.on(key)` уведомляет только подписчиков этого ключа, то есть O(1).
Лишних рендеров нет в обоих случаях, но со 100+ слоями разница в CPU заметна.

### Асинхронность и race conditions

Вся асинхронность живёт в `LayersController`, а не в `dispatch`. В vedro 1.1.0 async‑колбэк
определяется через `fn instanceof Promise`, а это всегда `false`, поэтому результат async‑dispatch
молча теряется.

Стратегия против гонок: у каждого слоя свой `AbortController`, и **его идентичность служит
«билетом» последнего запроса**.

- Новый запрос по слою или выключение слоя → `abort()` предыдущего.
- Ответ применяется, только если его контроллер всё ещё текущий для этого слоя.
- Это работает, даже если транспорт игнорирует `AbortSignal` (в тестах есть оба варианта).

Покрытые сценарии (`src/test/layersController.test.ts`):
- вкл→выкл: поздний ответ не «включает» слой обратно;
- вкл→выкл→вкл: старый ответ (успех или ошибка) не перетирает новый, даже если пришёл позже;
- retry работает только для включённого слоя в статусе error;
- при размонтировании все запросы прерываются (`dispose`).

### Компоненты и рендеры

- `LayerPanel` и `MapView` рендерятся один раз: они зависят только от статичного реестра и
  стабильного контроллера.
- `LayerRow` и `MapLayer` обёрнуты в `memo`. Пропсы — стабильные объекты конфигурации, каждый
  компонент подписан только на свой слой.
- Методы контроллера — стабильные стрелочные поля класса, поэтому `useCallback` не нужен.
- Значения контекстов не меняются, поэтому через контекст ничего не перерисовывается.
- Тест `src/test/renders.test.tsx` через `React.Profiler` проверяет, что переключение одного из
  150 слоёв перерисовывает **только эту строку** (2 коммита: loading, success), а изменение
  opacity — только свою строку.

### Типизация

`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, ESLint
`typescript-eslint/strict` + `no-explicit-any: error` и запрет non-null assertion. `LayerId` —
branded‑тип: идентификатор берётся только из реестра. Ошибки в `catch` типизированы как `unknown`.

### Масштабирование 5 → 100+

- Обновление одного слоя: O(1) подписчиков (`store.on(key)`), рендерится 1 строка + 1 оверлей.
- Добавить тип слоя — это одна запись в реестре. Логика и компоненты от количества слоёв не зависят.
- Проверить: `?layers=150` → «Включить все».
- Дальнейшие шаги для 1000+: виртуализация списка (`react-window`), ограничение параллельных
  запросов (очередь в контроллере), кеш данных слоя, чтобы повторное включение не ходило в сеть,
  батчинг `setAllEnabled` в один `dispatch`.
